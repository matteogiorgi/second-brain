# Note format

Conventions that every note of the [second brain](../areas/second-brain.md)
follows. They are the most rigid part of the [core](core-and-adapters.md):
changing them later means rewriting the archive.

## Files

- UTF-8 text, LF line endings, final newline.
- `.md` extension.
- Lines wrapped by hand at about 72 columns, like a commit message.

## Names

- Lowercase, words separated by hyphens, ASCII only:
  `compound-poisson-processes.md`, not `Compound Poisson processes.md`.
  Accents and capitals go in the text and the title, not in the file
  name.
- The name describes the content and is stable: a file is not renamed
  on a whim, because every rename breaks links.
- Exceptions with a fixed format: `journal/YYYY-MM-DD.md` and, in
  `inbox/`, the timestamped names generated by
  [capture](shell-capture.md).

## Frontmatter

Every note starts with a YAML block, except raw captures in `inbox/`
and `archive/inbox/`:

```yaml
---
title: Compound Poisson processes
tags: [probability, stochastic-methods]
created: 2026-09-25
---
```

- `title`: human-readable title.
- `tags`: a list, lowercase, kebab-case, ASCII like file names.
- `created`: ISO 8601 date.

Optional fields, only when needed: `updated` (date of the last
substantial revision), `source` (book, article, lecture the content
comes from).

`source` is a description that lets me find the source again (author,
title, chapter, URL, lecture date), not a file path. The source file
does not enter the archive: if it can be found elsewhere, the reference
is enough; if it is irreplaceable (my own notes, a photo of a
blackboard), it is kept outside, with a normal backup.

No other fields without first updating this note.

## Links

- Standard Markdown links with a path relative to the current file,
  extension included: `[Poisson process](poisson-process.md)`,
  `[second brain](../areas/second-brain.md)`.
- The link text reads as part of the sentence; no "click here".
- No `[[wikilinks]]`, no absolute paths.
- No links to sections (`note.md#section`) unless strictly necessary:
  every tool generates section anchors differently. If a section
  deserves a link, it probably deserves its own note.
- Link only to notes that exist. A concept that deserves a note but has
  none stays plain text until the note is written.

## Internal structure

- A single level-1 heading, equal to `title`.
- Level-2 sections; level 3 only if really needed.
- One idea per note. If two level-1 headings are needed, it is two
  notes.
- When a note records a choice, a **Why** section explains it.
- The last section is always **Links**, even if short; if there is a
  **Why**, it comes right before.

## Allowed extensions

Fenced code blocks name their language. Besides CommonMark, only
widespread extensions that stay readable as raw text:

- GitHub-style tables, for short data;
- LaTeX math between `$...$` and `$$...$$`.

Math is not CommonMark, but pandoc, GitHub and viewers with KaTeX or
MathJax support it, and it stays readable as source. It is a deliberate
compromise: for probability and statistics notes, giving it up would
cost more than the portability gained.

## Why

**Relative links instead of wikilinks.** Wikilinks are an extension:
they work only in the tools that implement them. Relative links are
understood by GitHub, pandoc, any Markdown viewer, and Vim follows them
with `gf`. They cost a few more characters, which the agent writes for
me.

**ASCII kebab-case names.** Safe in any shell without quoting, identical
on every file system, easy to tab-complete.

**Flat folders, structure in tags and links.** An idea can belong to
several topics; a folder forces it into one. And a note that never
moves never breaks the links pointing to it.

**Manual wrapping.** More readable git diffs and text that is
comfortable to read in a terminal. The serious alternative is one
sentence per line, which gives even cleaner diffs; I chose 72 columns
because they read better without a viewer.

**Minimal frontmatter.** Every extra field is a field to maintain on
hundreds of notes. Three required ones are enough to sort, filter and
date.
